# 0003. API Error Format and Documentation

- Status: Accepted
- Date: 2026-10-06
- Owner: Manav Gupta
- Reviewers: Team review pending
- Resolves: architecture pending decision 7; API design open decision 3 (partially)
- Threat model references: `TM-013`

## Context

The [API design](../phase-0/API_DESIGN.md) requires `application/problem+json` errors that never expose stack traces, SQL, payloads, or secrets, and an OpenAPI contract.

## Decision

- Errors use Spring's RFC 9457 `ProblemDetail` through one `@RestControllerAdvice`.
- Every response carries an `X-Correlation-Id` header. Problem bodies include the same value as `correlationId`. The value is generated by the server; inbound values are not trusted.
- Unexpected exceptions are logged server-side and returned as a generic `500` without exception details.
- Problem `type` stays `about:blank` until a canonical problem-type URI is chosen. Inventing a URI is deferred.
- The OpenAPI document is generated by springdoc-openapi at `/v3/api-docs` and shown at `/swagger-ui.html`. Only `/api/**` paths are documented.
- Both documentation endpoints can be disabled with `SECINTEL_API_DOCS_ENABLED=false`, and should be disabled or protected in shared deployments until authentication exists.

## Consequences

- Clients can rely on a single error shape for all `4xx` and `5xx` responses.
- CI verification of the published OpenAPI contract is a follow-up.
- springdoc is a community project outside the Spring portfolio; upgrades must track Spring Boot compatibility.
